## 今から変更するべき基盤

1. タスクをAI候補から独立させる。現在 tasks.candidate_id は必須で、Excel・手動タスクを直接作れない。nullable化し、origin（ai/manual/import）と出典リンクを追加する。AIタスクではcandidateを必須にし、既存の承認・重複防止を維持する。
2. 開始日 starts_on と元カテゴリ名を追加する。担当の実名をself/partnerへ勝手に対応させず、取込時に利用者が割り当てる。「共同」は二人担当として扱う。
3. UserとWeddingの1対1からMembershipを介した共有に移す。ユーザーは複数の結婚式へ参加可能、結婚式は複数の利用者を持てる。既存所有者をownerとして移行し、全クエリを所属するWeddingに限定する。
4. 通常のタスクを資料削除に巻き込まない。現行では資料→候補→タスクが連動削除される。将来はタスクを残して出典を解除する。削除予告画面・モデル・仕様・テストを同時に変更する。
5. ゲストと世帯を分離する。人数、席、料理は人単位、ご祝儀と引出物は原則世帯単位。集計のJOINで世帯金額を人数分増やさない。
6. 金額の見込み、請求・確定額、入出金実績を分離する。未入力の実績を0や見込額で埋めない。

## 画面と操作

- ダッシュボード：今週やること、期限超過、回答待ち、出席人数、見込負担額、支払期限を表示する。
- タスク：手入力、Excel取込、担当・カテゴリ・状態フィルタ。PCは一覧＋期間表示、スマホは期限順カードを基本にする。
- ゲスト・世帯：ゲスト編集、出欠、テーブル、世帯への関連付け。世帯詳細でご祝儀とギフトを編集する。
- 収支：見込と確定、支払予定と実績、数量根拠を比較する。想定ご祝儀と実際の受取を分ける。
- BGM：場面順に二人の候補と決定曲を表示。曲名とアーティスト、開始位置を扱い、音楽配信自体は範囲外。
- 資料と連絡：既存フローを継続。AIはタスク・変更候補を提示し、出欠や金額を自動確定しない。
- 設定：結婚式情報、メンバー招待、ギフト・祝儀区分、データ取込履歴、エクスポート。

スマホではPCの全列を縮小表示せず、一覧の要約から詳細編集へ遷移する。現状CSSではスマホでログアウトを非表示にしているため、モバイルのアカウントメニューへ戻す。入力文字サイズ、長いゲスト名、2列フォーム、画面キーボードによる隠れを実機で検証する。CSSにメディアクエリがあるだけでは操作確認済みとしない。

## 追加・変更するデータモデル（案）

すべての業務データはwedding_idを持つ。関連先が同じWeddingに属することをRails検証だけでなく、可能な箇所は複合外部キーでも保証する。日付はdate、時刻はtimezone付きdatetimeを使う。

| モデル | 主な項目・制約 |
|---|---|
| Membership | wedding_id, user_id, role(owner/editor)。組み合わせ一意。招待は期限・使用回数を制限したトークンのハッシュを保存 |
| Task | 既存項目＋starts_on, origin, category_raw, optional candidate_id。手動/取込時はAI候補を捏造しない |
| Household | code, name, cash_gift_rule_id, expected_override_yen, gift_set_id, notes。codeはWedding内一意 |
| Guest | household_id, name, side, relationship, age_group, attendance, invitation_status, seating_table_id, role, notes。招待状況は元ファイルに列がないためunknown |
| SeatingTable | wedding_id, label, capacity（任意）。コード一覧を実際に使用中の卓と混同しない |
| CashGiftRule | label, expected_yen。世帯の個別指定があれば優先 |
| GiftSet / GiftSetItem | 名称と商品構成。単価decimal、税込/税抜/不明、明示した税率、端数処理。既存注文の確定金額は設定変更で書き換えない |
| HouseholdGift | household_id, gift_set_id, quantity, delivery_status, confirmed_amount。世帯1セットを初期値にし例外数量を許容 |
| BudgetItem | income/expense, category, name, unit_price(decimal), quantity_mode, manual_quantity, tax_basis, tax_rate, service_charge, expected_override, confirmed_amount |
| Payment | budget_item_id等の対象、入金/出金、金額、日付。分割・一部払いを許容。ご祝儀はhousehold、交通費はguestへの関連を持つ |
| MusicCue | position, scene, selected_track, artist, start_offset_seconds, start_position_raw, notes |
| MusicPreference | music_cue_id, member_id（取込中は未割当可）, source_person_label, track_text。二人の希望と決定を分ける |
| ImportBatch / ImportRow | 元ファイルSHA256, mapping_version, status, dry_run, row key, 暗号化した元データ, エラー, destination_type/id, imported_version |
| SourceLink / ChangeEvent | タスク等の出典と変更者・変更時刻。個人情報を含む変更内容は暗号化 |

確定した支払額は整数円、税抜単価や計算中の値はdecimalで保持し、floatの誤差を避ける。四捨五入・切捨て等のルールと明細/請求単位の丸め位置を設定する。元ファイルだけから税区分や請求上の丸めを決めない。

氏名・世帯名・備考などの新規個人情報はRailsの暗号化対象にする。暗号化項目の検索方針は別途設計し、ブラウザからDBに直接アクセスさせない。ログに元行・氏名・鍵を出さない。

## 集計ルールと元Excelで要確認の箇所

- 今週のタスク：開始日<=日曜、期限>=月曜、未完了を基本とする。期限超過は別枠。開始日/期限の空欄は日付なしとして表示する。元「今週やること」のDUMMYFUNCTIONを実行せずタスクから再計算する。
- 世帯想定祝儀：出席者が1人以上の世帯だけを1回ずつ計上。個別設定があれば祝儀区分の初期値より優先する。未回答世帯は確定見込みに混ぜず、招待ベースの別シナリオにする。
- 出席者課金、大人のみ、子供のみ、対象者指定、テーブル数、手動数量を区別する。見積を確定した後は人数変更による差分を提示し、確定金額は自動更新しない。
- ギフト費用と交通費は明細と別集計に重複計上しない。統合後は収支計算に使う正本を決め、同じ支出の関連レコードは表示用にする。
- 見込負担額＝見込支出−見込収入。実際の未払残額は確定請求額と支払履歴から別途計算する。

| 元セル・範囲 | 確認内容 | 移行時の扱い |
|---|---|---|
| 世帯グループ!J2:J999 | 998個の式に#REF!が存在。現行ゲスト一覧には招待状況列がない | 招待ベース人数は未確定。出欠から招待状況を推測しない |
| ダッシュボード!H10:H11 | ギフト・お車代の「実績」が見込みセルを参照 | 実績を取込対象にせず、支払確認後に登録 |
| ダッシュボード!E13 | 見込総支出を一括1.1倍 | ギフト設定には1.08で割る式もある。税区分が混在するため明細別に確認し、元合計を正式金額にしない |
| ダッシュボード!E17 | 「1人あたり収支」でギフト費用を加算し、一部費用だけ差引 | 指標の意味を定義し直す。通常の全体収支/人数とは一致しない |
| 収支明細!D2:G5 | 「出席者」の行は手入力数量を使わず出席人数を参照 | 数量セルと適用数量を両方残す。実際に課金する対象人数を確認 |
| タスク一覧!B6,E6 | タイトル内の期限表現と期限列の日付が異なる | 期限列を候補値とし、不一致を警告。本文を書き換えない |
| タスク一覧!G46:G51 | メモ「同上」 | 元文字列を保持。前行の意味を自動で確定しない |
| タスク一覧!B1:B3 | 担当集計がC5:C42の固定範囲 | 追加された個人タスクも含む全件から再集計 |

この確認はデータ構造・数式参照の確認であり、実際の請求額・税務上の扱い・式場見積との一致を検証したものではない。

## Excel移行仕様

### 今回用意したもの

Git管理外の artifacts/excel-import-20260906/ に以下を置く。

- import_candidates.json：上表の入力行を英語キーへ対応付けた取込候補。全件review_required=true。氏名等の実データを含む。
- source_cells.json：元セルの値、数式、キャッシュ値、書式、色、コメント、リンク、結合範囲。数式のキャッシュは正しさ・鮮度を保証しない。Excel全機能のバックアップではないので元xlsxを残す。
- manifest.json：形式版、ファイルハッシュ、件数、DB未取込の記録。
- prepare_wedding_import.py：今回の2ファイル用の再抽出スクリプト。Pythonとopenpyxlを使用したローカル解析用。アプリの実行環境には追加しない。

tasksのcategory_raw/assignee_raw/status_rawは原語を保持する。名前のself/partner対応、カテゴリ分類、数式で求める金額は確定前に人が確認する。数式セルの対象値はnullとし、unverified_formulasへ元式とキャッシュを保存する。nullを0に変えない。

元データの実名・金額はGit管理する設計書・テストfixtureに転記しない。抽出JSONはローカルでのみ保存し、GitHub・外部AIへ送信しない。元Excelは変更していない。

### DB取り込み処理（目標仕様）

タスク用の実装済み部分と制限は task-import.md に記載。以下の複数種別の取込、差分更新、取消は今後の拡張仕様。

1. ログインしたユーザーの所属先Weddingを選ぶ。ファイル内のWedding IDは信用しない。
2. XLSX/JSONを解析し、ImportBatchへ保存する。ファイルサイズ・行数上限を設け、数式・マクロ・外部リンクを実行しない。
3. ドライランで担当・状態・カテゴリを対応付け、日付矛盾、世帯参照、空欄、金額の未確定を一覧表示する。
4. 元ファイルハッシュ＋sheet＋rowをsource_keyにする。同じWedding内で既取込のキーは追加しない。更新されたファイルは別ハッシュになるため、世帯コードと既存取込履歴から差分を提案し、氏名だけで自動統合しない。
5. 未解決の必須項目がある行は取り込まない。見出し・派生表示・サンプルの除外件数も表示し、利用者が対象行を確定する。
6. Railsの取込サービスからActiveRecord経由で保存し、暗号化・validationを適用する。マスタ→世帯→ゲスト→ギフト割当→収支→タスク/BGMの順で保存する。小規模バッチはトランザクションで一括確定する。
7. batchとrowに結果を保存し、二重送信時は既存結果を返す。取込後の手修正は再取込で上書きしない。
8. 取消は当該バッチの新規作成分だけを対象とし、変更版や依存先が増えていれば自動削除せず差分を提示する。更新分の復元にも同じ版検証を行う。

### SQLとSupabaseの位置づけ

「spabase」はSupabaseを指すと解釈する。SupabaseはPostgreSQLの配置先候補であり、Excelのデータ変換・確認を代行する仕組みではない。現在のRailsの暗号化フィールドに生のINSERT/COPYを行うと、暗号化やモデル検証を通せない。そのため本番業務テーブルへ直接投入しない。

SQLを使う場合は、Rails migrationによる構造変更、または権限を限定した一時ステージングまでにする。業務テーブルへの反映はRailsサービスが担う。RailsからSupabase Postgresへ接続する構成は可能だが、接続方式、SSL、接続数とSolid Queueの配置を確認してから採用する。既存のアプリDBとキューDBが分かれた構成を、接続URLだけでそのまま移せるとは扱わない。

公式接続資料：https://supabase.com/docs/guides/database/connecting-to-postgres

## 実装順と受入条件

### 第1段階：現在のExcelタスクを日常利用へ移す

Task独立化、開始日、手動追加、取込プレビュー、JSON/Excel取込、今週表示、担当フィルタを実装する。45件の状態・日付・メモが保持され、再取込で増えず、暗号化した値を画面で復号できること。実名の対応は確認が必要。

### 第2段階：夫婦共有・ゲスト・世帯

Membership移行、招待、ゲストと世帯、出欠・テーブル編集を実装する。64人・54世帯の件数と参照を照合し、出席47人・欠席3人・未回答14人の内訳を再現する。別WeddingをID指定しても読めない・変更できないことを検証する。

### 第3段階：ご祝儀・ギフト・収支

7祝儀区分・5ギフト設定・46明細を取り込む。金額確認が必要な項目は未確定で保持する。2人1世帯の二重計上防止、対象人数、欠席・未回答、税区分不明、0と空欄、分割払い、重複支出を架空データで検証する。

### 第4段階：BGMと連絡の統合

20場面と二人の希望を取り込み、決定曲と開始位置を編集できるようにする。AIは既存タスクの追加/変更候補を提示し、確認済み情報への上書きには利用者の判断を挟む。

全段階でスマホ幅375/390pxとPC幅1280px以上を確認し、ログイン、追加、編集、取込結果表示の主要操作をiPhone/Androidの実機でも検証する。PWAやストア配布はデータ共有の前提条件ではなく、必要に応じた追加とする。

## ローカル起動と配置

タスクとTaskImportのmigrationを追加・適用した。更新時はDockerでbuild、db:prepare、up -d web workerを順に実行する。既存の初期起動は README.md の bin/setup、次回起動は docker compose up -d を使う。詳細は task-import.md を参照。

本番公開は docs/deployment.md に従い、HTTPSでWebを公開、web/worker/DBを常時稼働させる。現在のdevelopment Composeをそのまま公開せず、production設定、暗号化キーの永続保管、DBと鍵の復元テストを用意する。DB移行時に暗号化キーを作り直さない。公開先やSupabaseプロジェクトの作成はまだ実施していない。
