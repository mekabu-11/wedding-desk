作成: 2026-09-07。状態: 設計・引継ぎ用。追加機能は未実装。

## 1. 目的・優先順位

2人がスマホ・PCから結婚式準備を管理し、現在の2つのExcelで行っている作業をアプリ内で完結させる。写真・スクリーンショット・文章を共通入口から登録し、必要時だけAIで複数領域の追加・更新候補を作る。

本書は会話の最新合意を統合した仕様。旧 `docs/wedding-preparation-design.md` の将来案と競合する場合は本書を優先する。既存機能を実装済み／未実装で区別する。旧設計にある4金額の並列入力、独立BGMメニュー、業者・支払先、注文数連動費という分類は採用しない。

ユーザー合意: レイアウト①、配色1、フォントA。ただし実物の参照を今回特定できていないため、それらの名称から具体的な外観を捏造しない。既存案の参照が見つからない場合は、機能実装を進めつつ最終的な外観だけ確認事項にする。

- 配置構成は既存のRender用設定＋Supabase PostgreSQLを継続。実際の稼働状況・契約プランは今回未確認。Vercelへの移設は本範囲に含めない。

## 4. データモデル

業務テーブルはwedding_idを持つ。全参照を同一Weddingに制限し、可能な参照は `(wedding_id, id)` の複合外部キーを使う。更新対象にlock_version、作成・更新日時を持つ。本文・氏名・備考・AI payload・変更内容は既存方針に沿って暗号化。金額計算はDecimal、保存する最終金額は整数円。nullと0を区別。

| モデル | 内容・主要制約 |
|---|---|
| Membership | user_id, wedding_id, role(owner/editor)。組合せ一意。v1は1人1Wedding、1Wedding最大2人。上限はWeddingロック下で保証 |
| Task | 既存項目維持。担当は表示名に依存しないperson_a/person_b/both/unknownへ移行。candidateは任意、AI起源にはSourceLinkが必要 |
| Household | wedding内一意code、名称、祝儀区分、メモ。招待単位として扱う |
| Guest | household、氏名、side、relationship、gender、adult/child、attendance、table、roles、allergies、notes。複数役割を許容 |
| SeatingTable | label, optional capacity。使用卓数は出席ゲストが配置された卓の数 |
| CashGiftRule | label, default_amount_yen。初期値の提案用。確定済み金額を一括上書きしない |
| GiftSet / GiftSetItem | セット名、引出物／引菓子／縁起物などの品名・単価・税区分・税率 |
| GiftAssignment | household_id, gift_set_id, quantity(初期1), included, budget_item_id。割当と予算明細は1対1 |
| PlanningItem | title, category, notes, position。例: 装花、入場BGM、ケーキ演出 |
| PlanningOption | planning_item_id, title, description, status(draft/considering/selected/rejected), optional reference_price_yen。1項目の採用候補は最大1件 |
| MusicDetail | PlanningOptionに任意で1対1。希望曲A/B、selected_track、artist、start_offset_seconds、元表記、scene。BGM固有項目を他分類に強制しない |
| BudgetItem | direction(income/expense), category, title, amount_yen(nullable), certainty(estimate/confirmed), inclusion(included/excluded), calculation_mode(manual/quantity), quantity_basis, unit_price, manual_quantity, tax_basis, tax_rate, rounding、source_kind、source_id |
| MoneyMovement | budget_item_id, occurred_on, kind(payment/receipt/refund/return), amount_yen(正数), note。支払い／受取履歴の正本 |
| PlanningCostLink | planning_item_id, budget_item_id。組合せ一意。複数対複数。リンク数を掛けて集計しない |
| TaskPlanningLink | task_id, planning_item_id。作業と検討内容を相互参照 |
| Document | 既存情報＋画像/PDF添付、memo、source日時。本文なし添付のみを許容。最低本文か添付が必要 |
| SourceLink | document_id, target_type/id, optional page/quote/region。型は許可リスト限定。同一Weddingを検証 |
| ChangeSet / ChangeOperation | AI/取込候補の束と個別操作。state、対象型/ID、作成時lock_version、暗号化したbefore/after、根拠、不明点、依存関係、反映結果 |
| ChangeEvent | actor, target, action, encrypted before/after, source。金額・採用案・出欠等の履歴 |
| ImportBatch / ImportRow | digest、mapping版、元sheet/row、暗号化元情報、行state、対象ID、実行結果、旧source_key対応 |

MoneyMovementはすべてBudgetItemにのみ所属。ご祝儀とお車代を別テーブルでも金額保存する二重管理はしない。BudgetItem.source_kindはmanual/cash_gift/travel_guest/travel_household/gift_assignment。ご祝儀は世帯につき1収入明細、お車代は個人または世帯につき1支出明細。BudgetItemの元関連は変更可能な一般ポリモーフィック入力にせず、許可型・同一Wedding・一意制約を保証する。

世帯のご祝儀・お車代やギフト割当を編集する画面は、裏側で対応BudgetItemを編集する。ゲスト画面にもお金画面にも同じ値が出る。

## 5. 2人での共有・既存移行

既存Weddingのuser_idからowner Membershipを作成し、現在の利用者・データを保持する。既存self/partnerはweddingのself_name/partner_nameをperson_a/person_bとして固定し、どちらでログインしても担当が逆転しない。

公開登録・メール招待サービスは作らない。管理コマンドで既存Weddingへ2人目のアカウントを追加し、通常のログインを利用する。パスワードは対話入力しログ／Gitに残さない。既存アカウントが別Weddingに所属していたら自動統合しない。

全コントローラ、添付ダウンロード、ジョブ、取込、関連付けをMembershipで限定。owner/editorとも業務編集可能。利用者削除でWeddingを連動削除しない。

## 6. 収支の確定ルール

### 日常入力

見える基本項目は「項目名」「金額」「概算／確定」「支払い」。業者・支払先を設けない。金額未確認はnull、追加費用なしは0。確定は金額必須。

金額を直接入力、または詳細で「単価×数量」から生成する。両方を同時編集できない。手入力へ切替時は現在値を引き継ぎ、自動計算を解除した旨を表示。

数量基準: 手動数量／出席者／出席大人／出席子供／出席世帯／使用テーブル。固定額は金額直接入力で扱う。注文数連動費という独立分類は作らない。適用数量を表示し、人数計算の結果と元見積の数量が違えば利用者が手動数量へ切替できる。

### 入出金

支払状況を別の正本として手入力保存しない。MoneyMovement合計から導出する。「全額支払済みにする」は不足額分の履歴を1件作るショートカット。日付を確認して保存。二重クリックを冪等キーで防ぐ。

- 支出の支払済み額 = payment − refund。
- 収入の受取済み額 = receipt − return。
- 金額>0: 正味0は未払い／未受取、0より多く金額未満は一部、同額は完了、超過は「超過・要確認」。
- 金額0・履歴なしは「支払い不要」。nullは「金額未確認」、残額も未確認。
- 残額 = amount − 正味入出金。概算なら「支払い見込み残り」、確定なら「未払い」。超過を0に丸めて隠さない。
- 元金額を減らして入出金合計を下回る場合は差分を表示して確認。過去の支払いを自動削除しない。
- 返金は過去payment合計、返戻はreceipt合計を超えない。誤登録は履歴付き訂正として処理する。

### 再計算・税

概算の数量連動明細は出欠・配席変更に追随し、変更前後を履歴へ記録。確定明細は単価・数量・税設定を固定し、人数変更時は差分候補だけ出す。

税区分は税込／税抜／不明。直接入力金額は支払総額として扱う。単価が税抜なら明示した税率で明細ごとに計算し、丸めは初期切捨て・明細ごと変更可。業務税率をAIが推測しない。不明なら確かな支払総額の手入力を求め、未確認件数を表示する。サービス料は必要時に通常明細として登録する。税務計算エンジンは作らない。

### 正本と集計

総支出／総収入は included のBudgetItemをIDごとに1回だけ集計する。概算を含む現時点の総額とし、未確認金額がある場合は「未確認N件を除く」と併記する。負担見込み = 総支出 − 総収入。

セット料金は1つの計上明細に複数PlanningItemを紐付ける。総額だけ判明なら内訳はメモ。正式内訳へ分解するときは元明細をexcludedにし、内訳合計との一致を検証して1トランザクションで置換。元明細に入出金がある場合v1では分解を禁止し、総額明細を維持する。

比較中のPlanningOption.reference_priceは収支に加算しない。採用時に「既存費用へ紐付け／費用追加／追加費用なし／金額未確認」を選ぶ。採用変更だけで旧費用の入出金や確定額を消さない。

### ゲスト由来の金額

ご祝儀の初期候補は出席者がいる世帯に祝儀区分金額を1回。未回答だけの世帯は自動計上せず、含める指定は可能。受取履歴がある世帯は出欠変更で除外しない。概算の除外・復帰にも履歴を残す。

引き出物はGiftAssignmentの明示割当と数量を使う。世帯の人数を掛けない。出席世帯へ1セットを一括提案できるが、承認前に作成しない。設定価格変更は概算のみ再計算、確定済みは差分表示。

お車代は個人／世帯のどちらに渡すか指定。世帯と所属個人の双方に登録されている場合は重複の可能性を表示し、理由付きで併存可能。自動合算・統合はしない。

## 7. タスク・ゲスト・検討の操作

- 今週は既存の開始日<=日曜、期限>=月曜、未完了条件を維持。日付なしは別表示。期限超過は別枠。
- ガントは開始日〜期限の横棒。期限のみはマーカー、日付なしは別一覧。PC週/月切替、スマホは横スクロール可能な任意ビュー。v1ではドラッグ編集・依存関係・自動日程調整を作らない。
- 一括変更は対象件数を示し、選択したIDとlock_versionに限定。フィルタ結果を全選択した時は全ページ対象である旨を表示。反映中に変更されたレコードは競合として再確認する。
- ゲスト出欠はinvited/planned等と混同しない。attendanceはattending/declined/pending/unanswered、招待状態は別任意項目。
- householdは手動登録時未設定可、元Excelの世帯参照が壊れていたら取込エラー。
- 検索はまずWedding内・上限2000件の復号後検索とし、氏名を平文複製した検索索引を作らない。絞り込み後、検索してからページング。上限超過は明示し、切り捨てない。
- 配席は卓ごとのメンバー一覧と移動操作。席の幾何配置・座席図エディタはv1対象外。
- BGMはPlanningItemをシーン順に表示。候補内に2人の希望、決定曲、再生開始位置を保持。実際の音楽再生・配信はしない。
- 一般の検討事項は候補1件でも登録できる。候補比較を必須にしない。

## 8. 画像・PDF・AI

Active Storageを使用。ローカルDockerは永続volume、本番は非公開オブジェクトストレージ。Supabase Storageの互換接続を実装時に公式資料で検証し、認証済みRails経由で保存・配信する。ブラウザに管理キーを渡さない。設定不備なら本番画像機能は公開不可。

受付: JPEG/PNG/WebP/HEIC・HEIF/PDF。画像はサーバーで向きを補正、EXIFを除いた表示用画像を作成。HEIC等は変換をDocker内で検証する。原本は非公開保存。SVGは受け付けない。ファイル拡張子だけで判定せずMIMEと実デコードを検証。

初期上限: 1ファイル20MB、1登録10ファイル、合計50MB、画像40メガピクセル、PDF20ページ、AI1回10ページ/画像。PDFは暗号化付き不可、外部参照・スクリプトを実行しない。上限超過は分割案内、黙って先頭だけ処理しない。長い変換・解析はジョブ化する。

AIの対象: Task、Guest、Household、PlanningItem/Option、MusicDetail、GiftSet/Assignment、BudgetItem、MoneyMovement、各関連。1入力から複数種別を提案できる。資料日時と入力日時を分け、相対日付の解釈基準を表示。

基本フロー: 原文保存→AI整理→変更プレビュー→選択して反映。明示した「決定」「参考」「検討中」タグを入力補助にする。画像だけで出欠、支払済み、採用、金額確定を推定しない。根拠のない補完は禁止。

ChangeOperation契約:

```json
{
  "key": "op-1",
  "action": "create|update|link",
  "entity_type": "許可した型",
  "target_id": null,
  "expected_lock_version": null,
  "attributes": {},
  "depends_on": [],
  "evidence": [{"document_id": 123, "attachment_id": null, "page": null, "quote": "原文の一部"}],
  "uncertainties": []
}
```

型ごとの属性許可リスト・型・最大長をサーバーで検証。wedding_id/user_id/任意SQL/任意モデル名をAIに指定させない。createは仮keyで後続操作から参照可能。文字引用は本文と照合し、画像根拠は該当ページをプレビュー表示する。根拠がなければ金額・人物・日時の重要変更は反映不可。

既存照合は同Wedding内。既取込ID・元コード・関連資料・名称等で候補を探し、名前一致だけで別人を統合しない。金額が同じだけで重複としない。新しい見積か別費用か判定不能なら要確認。

反映は選択操作＋依存操作を一括トランザクション。依存先を未選択なら反映不可、利用者に表示。再実行は同一結果、途中失敗は全件ロールバック。選択対象の版が変わっていたら全体を差分確認へ戻す。外部AI呼出中にDBロックを保持しない。

AIに削除・送金・外部連絡・自動決定を実行させない。API失敗時も元資料は保存済み、再試行可能。画像はAI整理を選んだ時のみ外部APIに送ることを入力画面に短く表示。全DBを毎回送らず、照合対象と必要な項目に限定。

既存全件整理は共通基盤完成後に対象件数上限100件/回で提供。選択・フィルタ結果・全件指定を分割処理し、結果プレビューは必須。v1の主要完了条件は写真／文章から複数領域へ登録できること。

## 9. 削除と履歴

資料削除は業務レコードを残す。SourceLinkと添付を削除し、変更履歴には「元資料削除済み」と保持。削除済み資料を実行中ジョブが再生成しない。

既存AIタスクのcandidate参照をnullableにするだけでなく、origin=aiならcandidate必須という現行DB制約をSourceLink/作成履歴に合う形へ移行する。Candidateのdependent destroyを解除する。既存candidate→task出典を先にSourceLinkへ移してから旧制約を切り替える。

入出金がある費用の削除は不可。除外・訂正して履歴を残す。世帯／ゲストは関連費用がある場合アーカイブとし、人数集計から外す前に影響を表示する。採用候補変更は旧候補・元金額の履歴を保持。

## 10. 初回Excel移行

対象2ファイルのための決定的パーサーを作る。Excel移行にAIを必須にしない。xlsxの数式・外部リンクを実行しない。展開後サイズ100MB、最大10000行の制限を設ける。認識しないテンプレートは説明付きで拒否。

件数目安: タスク45（区切り3行除外）、ゲスト64、名称あり世帯54、ギフト5、収支46、BGM20、祝儀区分7。世帯IDだけ残った99行を99世帯として登録してはいけない。目安はファイル更新で変わるため固定バリデーションにせず、実抽出の内訳を表示。

順番: マスタ→世帯→ゲスト→引き出物割当→収支→タスク→BGM。今週一覧／ダッシュボード／使い方サンプルは派生情報として取り込まない。BGMは20のPlanningItemへ変換し、希望・決定・元表記を保持。

担当A/Bを利用者が確認。カテゴリは元値を保持し対応表を表示。Excel「実績額」は支払額と断定せず、金額の採用候補として要確認にする。日付不明の入出金を捏造しない。世帯「実績ご祝儀」は受取候補として日付確認後に記録。

要確認: 招待人数の#REF!、実績に見込みを参照する式、一括税加算、元数量と人数式の不一致、タイトル中期限と期限列不一致。キャッシュ値を正式金額として無警告採用しない。

同一ファイルはdigestで二重取込を防ぎ、変更ファイルは世帯code・取込履歴を使って差分提示。既存TaskImport/source_keyを引き継ぎ、現行JSONで取り込んだタスクをxlsx移行で重ねない。名前だけの一致は要確認。

Railsサービス経由で一括反映。暗号化フィールドへSQL直投入しない。実データ・抽出JSON・画面写真をGitに入れない。移行確認後も元ファイルは保持。
